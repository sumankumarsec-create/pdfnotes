Two Sum in Java: How One HashMap Turns O(n²) into O(n)

7 August 2026 9 min read Java

Nearly everyone solves Two Sum on the first try. Almost nobody solves it the way the interviewer is waiting for, and the gap between those two things is one idea you can learn in about four minutes.

I want to be precise about what makes this problem worth your time, because it is not difficulty. Two Sum is genuinely easy. You will write something that works within a couple of minutes of reading it. That is exactly the trap: the first thing that works and the thing you are being tested on are two different programs, and the problem is designed so that the distance between them is small enough to walk but large enough to notice.

The problem

Given an array of integers nums and an integer target, return the indices of the two numbers that add up to target. The array is unsorted. You may assume there is at most one valid answer, and you may not use the same element twice.

So for nums = [2, 7, 11, 15] and target = 9, the answer is [0, 1], because 2 + 7 = 9. Note that it asks for indices, not values. That detail matters more than it looks, and I will come back to it.

The solution everyone writes first

Check every pair. Two nested loops, outer index i, inner index j starting at i + 1, and if nums[i] + nums[j] == target you are done. It is correct. It will pass. On an array of four elements it is instant.

The problem is that it examines roughly n²/2 pairs. At ten thousand elements that is fifty million comparisons. The interviewer's follow-up question is always some version of "what if the array is much bigger?", and the honest answer for the nested loop is that it falls over.

The nested loop asks, for every number, "which other number pairs with you?" — and then searches the whole array to find out. It re-reads data it has already seen.

That last sentence is the whole problem. The information needed to answer instantly was already in front of us; we just threw it away after looking at it.

The one idea

Stop searching for pairs. Search for the one number that would complete the pair you are holding.

If your target is 9 and you are currently looking at 7, you do not need to scan anything. There is exactly one number in the universe that finishes this pair, and it is 9 − 7 = 2. This is called the complement. The question changes from "is there a pair somewhere?" — which requires searching — to "have I already seen the number 2?" — which does not, provided you kept a record.

A HashMap is that record. As you walk the array, you store every number you have seen along with the index you saw it at. Before storing the current number, you ask the map whether its complement is already in there. A hash lookup takes constant time, so that question costs the same whether you have seen ten numbers or ten million.

One pass. One lookup per element. That is the whole algorithm.

The code

import java.util.HashMap;

public class Main {

    public static int[] twoSum(int[] nums, int target) {
        // value -> index of every number we have already passed
        HashMap<Integer, Integer> map = new HashMap<>();

        for (int i = 0; i < nums.length; i++) {
            int complement = target - nums[i];

            // Ask before storing. This is the important line.
            if (map.containsKey(complement)) {
                return new int[] { map.get(complement), i };
            }

            map.put(nums[i], i);
        }

        // No pair exists
        return new int[] { -1, -1 };
    }

    public static void main(String[] args) {
        int[] arr = { 2, 7, 11, 15 };
        int[] result = twoSum(arr, 9);
        System.out.println("Indices: [" + result[0] + ", " + result[1] + "]");
    }
}

Why you check before you store

This is the part that separates people who understand the solution from people who have memorised it. The order of those two operations is not stylistic. It is load-bearing, and it quietly solves two problems at once.

It stops an element pairing with itself

Suppose nums = [4, 3] and target = 8. At i = 0 the value is 4 and the complement is also 4. If you had stored 4 before checking, the map would contain 4, the lookup would succeed, and you would return [0, 0] — the same element used twice, which the problem forbids. Checking first means the map only ever holds numbers from strictly earlier positions, so a match is always two distinct elements.

It makes duplicates work

Now nums = [3, 3] and target = 6. At i = 0, the complement 3 is not in the empty map, so we store 3 → 0. At i = 1, the complement 3 is in the map, and we return [0, 1]. Correct. People often worry that map.put overwrites the first 3 and breaks this — it would, but we never get there, because we return before storing. Try that example in the visualiser above.

And this is why the problem asks for indices rather than values. Values would be ambiguous with duplicates; indices never are.

Worth noticing: the loop returns at index 1 and the last two elements are never examined at all. The O(n) figure is a worst case, not a promise about every input.

What it costs

Time complexity

O(n)

One pass over the array. Each hash lookup and insert is constant time on average, so the total is proportional to the number of elements — not to the number of pairs.

Space complexity

O(n)

In the worst case — no pair exists — every element ends up in the map. This is the trade you are making: memory in exchange for not re-scanning.

That trade is the actual lesson, and it generalises far beyond this problem. You had a quadratic algorithm and no extra memory. You spent linear memory and bought back a whole factor of n in time. Recognising when that trade is available is most of what "knowing DSA" means in practice.

The edge cases that catch people

  • Fewer than two elements. The loop runs zero or one time, nothing matches, and you return [-1, -1]. No special case needed — but say so out loud in an interview.
  • No valid pair. Same path. Decide deliberately whether you return a sentinel or throw; do not leave it undefined.
  • Negative numbers. They work without any change. nums = [-3, 4, 3, 90] with target = 0 returns [0, 2]. Subtraction does not care about sign.
  • Duplicates. Handled, for the reason above — but only because you check before you store.
  • Integer overflow. target - nums[i] can overflow int at the extremes of the range. Rarely tested, occasionally a bonus point if you mention it.

When this is the right approach

  • The array is unsorted and you are not allowed to sort it, or sorting would destroy the original indices you need to return.
  • You need better than O(n²) and you can afford O(n) extra memory.
  • Any single valid pair will do.

If the array were already sorted, the two-pointer technique would beat this — same O(n) time but O(1) space. If you needed every pair rather than one, the early return has to go. And if memory were genuinely tight, sorting a copy and using two pointers trades time for space in the opposite direction. Knowing which constraint you are actually under is the skill; the HashMap is just the tool that fits this particular one.

Where to go next

The complement idea is not really about Two Sum. It is the seed of an entire family of problems: subarray sums with a running total, pairs with a given difference, grouping anagrams by a canonical key. All of them are the same move — store what you have already seen so you never have to look at it twice.

If you want the pattern rather than the answer, work through the solved set below. And if you find yourself recognising this solution instantly without being able to explain why the check comes before the put, the other article is worth ten minutes of your time.
